Decision and implementation plan

PYRAX Website
Domain, UI and VPS Deployment Plan

A coordinated plan for replacing pyraxchain.com, aligning every PYRAX web property with the landing-page design system, and preparing the service ecosystem for a controlled VPS deployment.

Prepared: 5 September 2026
Scope: Marketing website, Explorer, Nodes, node portals, Devnet, Team Portal, shared UI, runtime services and VPS edge
Status: Audit and planning complete; implementation not started

Executive Summary

The PYRAX web repository is an ecosystem of separate Astro applications and supporting services. The domain change is not limited to visible navigation links: the old domain is embedded in RPC and WebSocket endpoints, wildcard node portals, staff authorization, reward eligibility, email senders, legal documents, CSP/CORS policies, telemetry, update feeds, SEO and reverse-proxy configuration.

The landing website should become the authoritative visual reference. Devnet already closely matches it, while Explorer, Nodes and Team Portal use older typography, color tokens and component geometry. Shared styling should be updated first, then adopted deliberately by each product.

Primary risk: A bulk search-and-replace could break staff access, node connectivity, browser security policies, RPC access, transactional email and installed clients. The migration must use a staged compatibility period.

Decisions Required

  • Approve the final apex domain.
  • Approve the complete subdomain and service hostname map.
  • Decide whether company email moves from @pyraxchain.com.
  • Decide whether Cloudflare will proxy public traffic or provide DNS only.
  • Confirm that pyrax-infra remains the deployment source of truth.
  • Set the required compatibility period for the old domain and installed node clients.

Domain Migration Plan

  1. Create one validated domain configuration shared by all applications.
  2. Move runtime URLs to explicit production environment variables where appropriate.
  3. Provision new DNS, TLS, RPC, WebSocket, status, update and email infrastructure first.
  4. Temporarily accept old and new staff email domains and security origins.
  5. Deploy backends and client-compatible tunnel endpoints before changing public links.
  6. Update navigation, visible copy, canonical URLs, sitemap, robots, legal text and email templates.
  7. Smoke-test HTTP, RPC, WebSocket, OTP, push, CORS, CSP and wildcard node portals.
  8. Redirect old web hosts; retain operational endpoints until usage telemetry confirms retirement is safe.

UI Design Direction

The landing page is the canonical PYRAX system: Instrument Sans for body copy, Unbounded for display text, JetBrains Mono for technical metadata, near-black fields, restrained orange fire and blue water accents, mono eyebrow labels, outlined display type, compact glass chrome and disciplined section dividers.

Marketing pages may remain expressive. Explorer, Devnet and Team Portal should keep compact operational density rather than inheriting oversized landing-page typography or decorative layouts.

Landing Website

  • Preserve the current visual direction and use it as the reference implementation.
  • Standardize headers, spacing, CTAs, tables and mobile behavior across Technology, Network, Token, Developers, Company, Industries, Whitepaper, Pitch, Privacy and Terms.
  • Update all service links and SEO metadata through the centralized domain map.

Explorer

  • Replace older Inter/Sora typography and color values with canonical tokens.
  • Keep the dense sidebar and data-oriented shell; align logo, 64px chrome and active navigation.
  • Add compact technical page headers and consistent tables, filters, pagination, focus, loading, empty, offline and error states.
  • Use approximately 8px radii for operational panels.

Nodes and Node Portals

  • Reframe the public hero using the landing page's technical visual language.
  • Align typography, navigation, footer, status treatments and responsive behavior.
  • Standardize Run, Downloads, Map, Peers, Remote and Notify pages.
  • Migrate wildcard parsing, CSP, service-worker URLs and tunnel registration with an overlap window.

Devnet Portal

  • Preserve its current operational shell; it is already closest to the landing system.
  • Reduce decorative radial elements, nested rounded panels and excessive glass layering.
  • Align headers, empty states, controls, tables and dialogs; use icons for close actions.
  • Verify authentication, onboarding, training, missions, chat, pairing, uploads, push and rewards.

Team Portal

  • Migrate to canonical typography and colors.
  • Share the Devnet authentication-shell pattern while retaining a quiet internal tone.
  • Align sidebar, header, navigation, dialogs, tables and compact panel geometry.
  • Carefully migrate email identities, superuser defaults and service integrations.

Shared UI Foundation

  • Move current landing tokens and primitives into pyrax-shared.
  • Centralize fonts, colors, buttons, inputs, focus treatment, panel geometry, metadata and shared chrome.
  • Keep application global styles limited to genuine product-specific behavior.

VPS Readiness Findings

  • The repository references a root docker-compose.yml, but that file is absent. The checkout cannot independently prove an end-to-end deployment.
  • Current workflows indicate that the separate pyrax-infra repository builds images, owns Compose and performs deployment.
  • Deployment documentation and Caddy routing omit or disagree about Devnet, chat, wildcard node portals and several supporting services.
  • Wildcard node TLS requires a Caddy build containing the Cloudflare DNS module and a scoped DNS token.
  • The documented secret list is incomplete for current Nodes, Devnet, Team, databases, VAPID and administration features.
  • Most container health checks prove liveness, not readiness. External checks must cover database health, indexer lag, RPC, WebSockets, email, tunnels and faucet behavior.
  • Claims of zero downtime and easy rollback need verification against the actual infrastructure configuration.

Phased VPS Plan

Phase 0: Decision Freeze

Approve domains, email policy, Cloudflare topology, service ownership and the canonical infrastructure repository.

Phase 1: Reconcile Infrastructure

Audit pyrax-infra; align Compose service names, ports, networks, volumes, health checks, secrets, Caddy routes and documentation.

Phase 2: Domain Compatibility

Centralize endpoints, prepare new DNS and certificates, add dual-domain security allowances, and update node/tunnel clients before public cutover.

Phase 3: VPS Hardening and Data

Use restricted SSH access, minimal public ports, private database networking, protected secrets, resource limits, log rotation, persistent storage and backups.

Phase 4: Staging

Deploy immutable image tags under staging names and test every page, API, RPC, WebSocket, authentication, email, database, indexer, tunnel and faucet workflow. Test restart and rollback.

Phase 5: Production Rollout

Lower DNS TTL, snapshot data, deploy the edge, then stateless services, then stateful services. Health-gate each step before switching DNS.

Phase 6: Operations

Add uptime/readiness alerts, logs and metrics, disk and certificate monitoring, backup restore drills and rotation schedules. Retire old endpoints only when telemetry supports it.

Recommended Execution Order

  1. Approve the final domain and email map.
  2. Reconcile infrastructure, Compose, Caddy and deployment documentation.
  3. Centralize domains and introduce temporary dual-domain compatibility.
  4. Centralize the landing design system in pyrax-shared.
  5. Update Explorer, Nodes, Team and Devnet.
  6. Run responsive screenshots and accessibility checks at desktop, tablet and mobile widths.
  7. Deploy and validate staging.
  8. Migrate production DNS while monitoring both domains.
  9. Retire old endpoints only after client and traffic data show they are unused.

Acceptance Checklist

  • Every public route uses the approved hostname map.
  • No unintended pyraxchain.com runtime dependency remains.
  • Old-domain redirects preserve paths and query strings.
  • RPC, WebSockets, CORS, CSP, OTP, email, push and node tunnels pass production smoke tests.
  • Explorer, Nodes, Devnet and Team visually use the landing design tokens.
  • Operational screens retain compact, usable information density.
  • Desktop, tablet and mobile screenshots show no overflow or overlap.
  • Backups and rollback are tested, not only documented.
  • Monitoring covers service readiness and business-critical workflows.
